# 完整改写与场景示例

以下均为虚构的通用案例。输入与预期输出用于人工核对语义，未做真实模型对照；复用判断方法，不照搬案例的业务规则或章节。

## 案例一：简单提取，保留最小表达

任务是从会议记录提取明确承诺且尚未完成的待办，返回固定字段。现有初稿的要求基本正确，但同一判断重复出现。

### 原稿

```text
你负责从会议记录中整理待办，需要认真理解每个人的发言，准确识别真正需要完成的工作。

处理时先完整阅读会议记录，再筛选待办。要区分明确承诺、一般建议和已经完成的事情，只留下参会人明确承诺且尚未完成的事项。没有承诺的建议不算待办，已经完成的事项也不要留下。

对每条待办识别任务、负责人和期限。负责人或期限没有明确说出时不要猜测，对应字段填 null。没有符合条件的事项时返回空数组。

最终只输出 JSON 数组，每项有 task、owner、deadline 三个字段。输出前再次检查每条事项都属于明确承诺且尚未完成的工作，不要加入解释。

会议记录：
{{meeting_notes}}
```

### 改稿

```text
从会议记录中提取参会人明确承诺且尚未完成的待办。只输出 JSON 数组，每项包含 task、owner、deadline；负责人或期限未明确时填 null，没有符合条件的事项时返回 []。

会议记录：
{{meeting_notes}}
```

“明确承诺且尚未完成”已经给出筛选判据，无需另列阅读、筛选、复查流程。空值与无结果的出口仍保留；任务只有一个判断，不需要为了 ICTIO 拆出多个标题。

### 语义核对

输入：

```text
林晓：我周五之前把接口文档补好。
陈宇：也许可以加个筛选按钮。
林晓：上周的故障复盘已经发出了。
周岚：我来核对那份清单，时间还没定。
```

预期输出：

```json
[
  {"task": "补全接口文档", "owner": "林晓", "deadline": "周五之前"},
  {"task": "核对清单", "owner": "周岚", "deadline": null}
]
```

一般建议与已完成事项被排除，未明确的期限保持空值。如果记录只有建议或已完成事项，应返回 `[]`。

## 案例二：资料问答，先理清条件再组织文本

任务是依据提供的帮助文档回答产品问题。用户要求先梳理逻辑，再看成稿；不同套餐或版本可能影响答案，资料也可能冲突或缺失。

### 原稿

```text
你是产品帮助助手，请结合用户问题、历史对话和帮助文档，灵活判断应该回答什么，提供准确、清楚、自然的中文回复。用户不一定会说产品、套餐和版本，必要时要问清楚，但已经在对话中说过的就不用再问，也不要每次都问一遍。

只依据提供的帮助文档回答，不用外部知识补充。文档不一定都适合当前产品、套餐和版本，要看适用范围。如果缺少的信息会影响答案，需要先确认；如果不同情况答案相同，就不用追问。

回复先说结论，再给必要步骤，引用文档的结论后标注编号，不超过三句话，不扩展无关建议。资料没有写的内容不能猜，但没有写不等于产品不支持，可以说明资料没有覆盖。

有时文档之间会不一致。要先看是否都适用于当前情况，确实冲突时告诉用户有冲突，说明对应文档，暂时不要替用户选一个结论。不能只因为某篇发布时间更晚就认为它更可信。

必须充分理解上下文，避免不必要的追问。缺少影响判断的信息时，本轮先问清楚，不要一边追问一边先给出某个版本的结论。信息足够且文档一致时再直接回答。

历史对话：
{{conversation}}

帮助文档（含编号与适用范围）：
{{documents}}

用户问题：
{{question}}
```

### 先对齐核心逻辑

此时先向用户说明：

> 先利用对话中已有的信息核对文档适用范围。缺失信息会改变答案时，只追问这一缺口；适用文档互相冲突时，指出冲突并保留结论；资料未覆盖时，如实说明。依据明确后，再给结论与必要步骤。

原稿中的“必要时追问”由“缺失信息是否改变答案”决定。适用范围必须先于冲突判断，否则不同套餐的正常差异也会被当成矛盾。用户认可这条逻辑后，沿用它组织全文。

### 完整改稿

System：

```markdown
# instruction

依据提供的帮助文档回答用户当前的问题，沿用对话中已确认的产品、套餐和版本。

## workflow

1. 根据已知信息筛选适用文档。若缺失的产品、套餐或版本信息会改变答案，本轮只追问影响判断的信息；不同情况下答案相同时，直接继续。
2. 若适用文档对当前问题存在冲突，说明冲突及对应文档，暂不作出结论；不因发布时间较晚就采信其中一篇。
3. 若适用文档未覆盖当前问题，说明资料未覆盖，不据此判断产品不支持。
4. 依据明确且足以回答时，先给结论，再提供完成当前任务所需的步骤；不补充文档以外的知识或无关建议。

## examples

以下示范资料如何决定回答，示例内容不作为本次问题的依据。

- 套餐不同会改变答案，当前套餐未知
  > 资料：基础版只支持导出 TXT，专业版还支持导出 PDF。
  > 输入：怎么导出 PDF？
  > 输出：你使用的是基础版还是专业版？

- 套餐不同但答案相同
  > 资料：[D1] 基础版支持导出 TXT；[D2] 专业版支持导出 TXT。
  > 输入：支持导出 TXT 吗？
  > 输出：支持，两种套餐都可以导出 TXT。[D1][D2]

- 适用文档互相冲突
  > 资料：[D3] 专业版 2.0 支持导出 PDF；[D4] 专业版 2.0 不支持导出 PDF。
  > 输入：专业版 2.0 能导出 PDF 吗？
  > 输出：两份文档对专业版 2.0 的说明有冲突，暂时无法确认是否支持导出 PDF。[D3][D4]

- 资料未覆盖当前问题
  > 资料：只说明专业版支持导出 TXT 和 PDF，没有说明其他格式。
  > 输入：专业版能导出 EPUB 吗？
  > 输出：当前资料未说明专业版是否支持导出 EPUB。
```

User：

```markdown
# Context

<history>
{{conversation}}
</history>

<documents>
{{documents}}
</documents>

# Input

<question>
{{question}}
</question>

# Output

用简洁、自然的中文直接回复，不超过三句话。引用文档的结论后标注编号，如 [D1]。
```

各条件按依赖展开：先确定哪些文档适用，再判断依据能否支持回答。重复出现的追问要求合并到第一步，文风与引用格式集中到 Output。示例以相同的“资料、输入、输出”结构区分四个分支；保留原稿的三句上限与三个变量，没有新增检索工具或资料优先级。

### 语义核对

输入材料：

```text
历史对话：用户已确认使用星河笔记 2.0，未说明套餐。

[D1] 星河笔记 2.0，基础版：支持导出 TXT，不支持导出 PDF。
[D2] 星河笔记 2.0，专业版：支持导出 TXT 和 PDF。导出 PDF 时，在文档菜单中选择“导出 → PDF”。

用户问题：怎么导出 PDF？
```

预期回复：

> 你使用的是基础版还是专业版？

如果用户接着回答“专业版”，沿用已知产品和版本，预期回复：

> 专业版支持导出 PDF，在文档菜单中选择“导出 → PDF”即可。[D2]

其他分支用同一组材料作局部变更核对：

| 情况 | 预期行为 |
| --- | --- |
| 套餐仍未知，用户问是否支持 TXT | 两种套餐答案相同，直接回答支持，并引用 D1、D2。 |
| 已确认专业版，新增同样适用的 D3，写明不支持 PDF | 指出 D2 与 D3 冲突，暂不确认是否支持；不按发布时间选边。 |
| 已确认专业版，用户问能否导出 EPUB | 说明当前资料未覆盖 EPUB，不推断为不支持。 |

### 后续只修改表达

用户反馈：“逻辑没问题，把回复改得更像同事聊天，三句话的限制保留。”

这轮只需替换 Output 的第一句：

> 用同事之间自然、直接的语气回复，不超过三句话。

引用要求与前面的判断流程继续保留。反馈没有改变业务判断，无需重写全文或重新确认套餐规则。

## 生成任务：示范完整成品

假设任务是根据已发布功能的资料写更新通知，只输出 `{"body":"正文"}`。正文为两句话、20–60 字符，含标点不含空白；只写资料提供的功能与操作步骤。

“先告知功能，再说明入口”是写作策略，应写入指令。few-shot 要展示完成这项策略后的通知正文，并满足同一输出契约。

```markdown
## examples

以下为合成输入及完整通知，不作为本次发布事实。

- 文档新增导出格式
  > 输入：{"feature":"文档支持导出 PDF","steps":"打开文档菜单，选择‘导出 → PDF’"}
  > 输出：{"body":"文档现已支持导出 PDF。打开文档菜单，选择‘导出 → PDF’即可。"}

- 素材库新增批量操作
  > 输入：{"feature":"图片支持批量上传","steps":"打开素材库，点击‘上传’，选择多张图片"}
  > 输出：{"body":"图片现已支持批量上传。打开素材库，点击‘上传’，选择多张图片即可。"}
```

这两条输出可直接作为该任务的最终结果：字段、句数与长度符合约定，功能和步骤均来自对应输入。优化旧稿时保留其中有效的选材边界，但不能把边界说明换个标签继续当作 few-shot。

## 对话人格：场景与回应

假设用户已经明确：以平等、直接的语气聊天，尊重对方是否需要建议、是否愿意继续。下面只示范互动方式；知识问答的“资料、输入、输出”无需照搬到人格对话中。

```markdown
## examples

以下示范回应方式与对话节奏，不要求复用固定措辞。

- 用户只想倾诉，暂时不要建议
  > 用户：让我吐槽两句，先别给建议。
  > 助手：说吧，我先听你讲。

- 用户已经决定结束对话
  > 用户：行，我先去忙了。
  > 助手：好，回头聊。
```

若只示范文风，场景已经交代清楚，就可以直接给文案：

```markdown
## examples

以下只示范简短、自然的回应语气。

- 对方已经决定结束对话
  > 好，回头聊。
```

## 功能任务：场景与工具交互

假设既有接口要求 `create_reminder` 接收 `title`、`time`，时区已知为 UTC+8；缺少时间先询问，工具返回 `created` 后才能确认创建成功。以下工具与接口均为虚构示范。

```markdown
## examples

以下示范缺少参数时的追问，以及工具确认后的答复。工具返回仅代表该示例中的结果。

- 缺少提醒时间
  > 用户：提醒我提交周报。
  > 助手：什么时候提醒你？

- 参数齐全，工具确认创建成功
  > 用户：2026 年 11 月 5 日上午 9 点提醒我提交周报。
  > 工具调用：create_reminder({"title":"提交周报","time":"2026-11-05T09:00:00+08:00"})
  > 工具返回：{"status":"created"}
  > 助手：已设好，11 月 5 日上午 9 点提醒你提交周报。
```

三类示例共用“无序场景标题＋引用块”，引用块内部保留当前任务所需的角色、依据或结构。工具参数、工具返回和面向用户的文案分别标记，避免把一次调用意图当作已经完成。
