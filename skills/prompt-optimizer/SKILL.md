# Prompt Optimizer

根据用户需求优化提示词的逻辑、表达与结构。沿用已经确认的目标、输入输出约定和有效内容，交付可直接审阅的候选稿；文件修改、模型调用与系统发布按用户要求的范围执行。

## 突出功能重点

先明确用户要完成什么，哪些判断和行为决定结果，再确定指令重点与章节顺序。

| 功能重点 | 指令优先说清什么 |
| --- | --- |
| 对话人格 | 身份与关系目标、交流风格、不同情境下如何回应和推进对话。 |
| 功能任务 | 判断依据、必要输入、分流条件与处理结果；涉及工具时说明参数来源和调用后的反馈。 |
| 知识问答 | 问题范围、信息来源、证据是否足够，以及如何形成回答。 |

同一任务可以兼有多种能力，以用户当前目标确定主次。人格要求不能淹没功能判断，工具过程也不应挤占用户真正需要的回答。

## 理清判断逻辑

先明确模型依据什么信息、作出什么判断、据此采取什么动作。区分用户的目标、必须满足的约束和举例；典型例子不能擅自变成完整范围，含混说法也不能直接固化成业务规则。无法从已有材料确定的策略，指出待定之处。

按判断依赖组织动作：先得到依据，再作选择，最后表达或执行。在实际分流处写明条件、优先级和对应动作；任务允许无结果、依据不足或无需行动时，保留相应出口。检查相邻步骤是否能衔接，避免先选结论、再找依据。

每项要求集中表达。只在某个分支生效的规则放到该分支，通用约束统一说明；流程已经表达的内容无需再抄进 rules。合并时保留原有的条件、例外与适用范围。

## 提炼准确表达

把抽象期待落实到具体动作，用准确的动词、对象与条件替换铺垫和含混指代。例如，“将订单放入当前上下文，观察它是否与用户所说的内容相符”可改为“核对订单是否匹配用户提供的信息”。“充分理解、灵活处理、确保准确”本身不足以说明如何判断，需要结合任务已有的判据展开。

逐句检查它增加了什么目标、依据、动作、条件或边界，删除同义重复和不改变行为的铺垫。保留完整、自然的语句，以快速理解为准；不要靠生硬缩写压字数，也不要为凑篇幅扩写。背景事实和字段说明按其用途表达，无需全部改成命令句。

## 按职责重排结构

[ICTIO](https://echouser005.github.io/posts/how-the-ictio-framework-improves-the-maintainability-of-engineered-prompts/) 区分五种内容：Instruction 写目标与执行逻辑，Context 放背景和参考资料，Tools 说明工具能力与调用约定，Input 放本次处理对象，Output 定义结果格式与表达要求。

下面是可裁剪的布局，不要求补齐全部章节。一级标题区分内容职责，二级标题展开指令；System、User 表示消息角色。

```text
System
├─ # instruction
│  ├─ 任务目标；必要时补充角色与风格
│  ├─ ## workflow    有前后依赖的判断与动作
│  ├─ ## rules       流程未覆盖的独立约束
│  └─ ## examples    场景与示范
└─ # Tools           工具能力、调用条件和结果处理

User
├─ # Context         背景、历史与参考资料
├─ # Input           本次请求或待处理对象
└─ # Output          输出结构与表达要求
```

一句能说清任务时就保留一句。需要顺序执行时用编号写 workflow；对话人格等按情境选择行为的任务，可用 strategies 组织无序策略，不硬造执行流程。role、style 等内容按功能需要在 instruction 内展开。

把关键目标放在开头，长资料集中分区，当前输入与输出要求靠近结尾；这是参考 [Lost in the Middle](https://arxiv.org/abs/2307.03172) 的布局起点，具体顺序仍按任务和模型调整。已有稳定输出契约可保留在 System，不在两处重复维护。

用有语义的标签区分资料来源，并与变量占位符对应，如 `<history>{{history}}</history>`。保留来源、时间和不确定状态；区分未知与否定，区分参考资料与当前输入。已有消息角色、变量和运行时必需的格式约定保持兼容。

## 按场景组织示例

先按当前任务的最终交付物设计示例：生成任务给完整成品，提取与分类任务给约定结果，工具任务给调用及返回支持的答复。few-shot 的输出必须符合任务的格式、长度和内容约束；“处理、思路、应该怎么写”属于执行策略，不能替代输出。

统一用无序列表写场景或关键条件，用缩进的 `>` 引用块承载示例；并列场景不表示执行顺序。

```markdown
## examples

以下示范待办提取，示例内容不作为本次会议事实。

- 明确承诺，期限已知
  > 输入：小周说：“我周五前提交方案。”
  > 输出：[{"task":"提交方案","owner":"小周","deadline":"周五前"}]

- 只有建议，没有承诺
  > 输入：小周说：“也许可以补一张图。”
  > 输出：[]
```

示例提供足以支持结果的输入；合成材料明确标注。对话用角色标签保留轮次，工具示例区分请求、调用参数、工具返回与最终答复。只校准文风时，场景后可直接给符合要求的完整文案；字段占位符和 schema 放在 Output 说明格式，不充当成品示例。

原稿只有选材边界或处理说明时，保留判据并归入 workflow/rules，再补完整示范；用户认可的成品示例优先保留。选择能体现核心行为或区分关键分支的场景，同一组示例使用一致的字段和标记。示例中的事实、具体措辞和动作不自动成为通用规则。

完整改写与三类示例见[案例](references/rewrite-examples.md)。

## 核对与交付

核对业务含义、变量、输出契约及示例是否一致，再通读目标、判断顺序、分支出口是否清楚。用户只改局部时，保留其他已认可内容；需要成稿时，直接给完整候选和关键改动。缺少资料或工具能力时说明缺口，不用措辞补造能力。

实际效果需要验证时，使用原有[评测方法](references/evaluation.md)，区分语义核对与模型结果，不以缩短字数或格式通过代替效果改善。
